# Science Before Bookkeeping

> **Do the science. Deliver the supported result. Package last, if needed.**

Treating file hashes or byte parity as scientific correctness controls is a
fundamental category error. Identical bytes can preserve the same wrong physics,
wrong units or unsupported inference perfectly. Administrative consistency is not
a measurement, a numerical error estimate or evidence that a model describes nature.

Active scientific production, reasoning and physical results take priority over
optional administrative work. This is a workflow policy, not a claim that integrity
checks are useless or an exemption from binding project requirements. Apply the
optional `thinking-like-a-scientist` skill alongside it when available; this skill
does not require another installed directory.

## Do not confuse kinds of evidence

| Observation | What it establishes | What it does not establish by itself |
|---|---|---|
| Matching file hashes or byte parity | Byte identity for the compared artifacts, subject to the comparison's assumptions | Correct physics, applicable calibration, numerical accuracy or supported inference |
| A successful command | The observed execution completed successfully | That its outputs answer the scientific question correctly |
| A passing test | The tested behavior met the assertions and oracle actually exercised | Physical validity outside those checks, model adequacy or observational support |
| An independent numerical or physical comparison | Evidence for the assessed quantity, precision and applicability | Universal correctness beyond that assessed scope |

Tests can supply real numerical evidence when their expectations are independent
and scientifically justified. Do not reduce that evidence to a pass count, and do
not mistake a regression against yesterday's unverified output for an independent
reference. Keep useful tests in active development; packaging-last is not testing-last.

## Finish the scientific work before packaging

Until the requested scientific objective has been fully achieved, do not introduce
or run optional hash inventories, checksum tracking, byte-parity certification or
byte-freezing. Do not require these before exploration, method development,
debugging, fitting, interpretation or an otherwise justified independent calculation.
An absent or stale packaging hash is not a scientific blocker.

Choose the next action by the physical or numerical uncertainty it resolves:

- Identify the requested observable, precision and competing explanations.
- Inspect the actual inputs, units, assumptions and uncertainty relevant to that
  question. Use existing trustworthy inputs and records; do not invent observations.
- Perform the smallest discriminating calculation or independent comparison with
  enough precision to resolve the question. Investigate model adequacy as well as
  implementation, numerical error and sampling behavior where applicable.
- When repair is requested, correct the actual consumer and measure the scientific
  before/after effect. Keep focused regression coverage; a diagnosis alone is not
  a completed repair.
- Preserve raw inputs and failures, and retain enough configuration, units, source
  version and outputs to understand the experiment using existing records. Do not
  turn that compact record into a new checksum-ledger or provenance-audit project.

Fully achieved means the scoped question has a supported answer at its required
precision and applicability, or the requested capability has been repaired and
assessed. It does not mean absolute certainty or a preferred positive verdict.
A defensible bound or demonstrated ambiguity may answer a measurement question;
a status label or caveat does not finish an unresolved repair.

If blocked, state what was attempted, what was learned, the actual missing input
or capability, and the next feasible route. Continue independent justified work
within authorization. Do not substitute a tidy package for unfinished science.

## Hashing belongs at the absolute end, and may be unnecessary

Only after the scientific objective is fully achieved may optional packaging
operations begin. Only then, if the requested delivery actually needs them, generate
checksums, certify distributed-file parity or freeze the completed deliverable.
If packaging was not requested and no binding requirement calls for it, skip it.

Describe these operations as packaging or transfer-integrity checks, never as
scientific validation. Do not create hash receipts, manifests, release bundles or
new acceptance stages by default. A later scientific discrepancy reopens the
scientific work; preserving yesterday's package is not a reason to defend a wrong
calculation or silently exclude a failing case.

## Preserve genuine integrity and protected evaluation boundaries

Do not use this priority rule to ignore actual corruption, unknown units,
wrong-source inputs, security checks or protected/blinded material. Stop only the
affected unsupported calculation and resolve its concrete input problem; this
does not automatically require a project-wide lineage audit. Missing historical
metadata may restrict adoption of an old result without preventing a new calculation
on adequately identified inputs.

Existing mandatory transport checks, resource-mirror contracts, source checks and
blind-evaluation freezes are not optional packaging invented by this skill. Honor
them narrowly at their actual boundary; a required checksum can detect corruption,
not certify the physics. Do not disable safeguards, alter protected answers or
silently bypass a binding requirement. If a requirement genuinely blocks the task,
identify the exact conflict and seek an authorized change instead of inventing more
gates. This skill grants no new compute, release, publication or data-access authority.

## Examples of the intended decisions

| Situation | Science-first response |
|---|---|
| Tests pass and output hashes match, but a physical normalization is wrong. | Repair the normalization at the real consumer and measure its effect against an independent expectation; matching bytes do not defend it. |
| A bounded comparison has known inputs and units but no release manifest. | Run the authorized comparison; do not create a hash inventory as an entry ticket. |
| A required download checksum identifies a corrupt calibration file. | Reject that affected input and obtain a trustworthy replacement; do not call corruption an optional packaging concern. |
| The scientific result and uncertainty are delivered; no archive or bundle was requested. | Stop. Do not add a checksum campaign to manufacture another milestone. |

Lead progress reports with the physical finding, measured precision or effect,
remaining scientific gap and next justified action. Put software checks behind
that answer, with their actual scope. **Never present byte identity, a green test
or administrative readiness as the scientific achievement.**
